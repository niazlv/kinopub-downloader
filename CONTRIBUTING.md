# Участие в разработке

Спасибо за интерес к проекту. Ниже — то, что стоит знать перед первым pull request.

## Лицензия вашего вклада

Проект распространяется под [GPL-3.0-or-later](LICENSE).

Отправляя pull request, вы соглашаетесь, что ваш вклад лицензируется на тех же условиях. Это правило «inbound = outbound» из [Условий использования GitHub, раздел D.6](https://docs.github.com/site-policy/github-terms/github-terms-of-service#6-contributions-under-repository-license) — оно действует автоматически для любого репозитория, в котором есть файл лицензии, так что отдельную бумагу (CLA) подписывать не нужно.

Отправляйте только тот код, который вправе лицензировать: свой собственный либо совместимый с GPL-3.0 и с сохранённым исходным копирайтом.

## Заголовки файлов

Каждый файл с исходным кодом начинается с копирайта и машиночитаемого SPDX-тега:

```go
// Copyright (C) 2026 niazlv <niazlv03@gmail.com>
// SPDX-License-Identifier: GPL-3.0-or-later
```

В новых файлах ставьте **своё** имя — авторство сохраняется за вами:

```go
// Copyright (C) 2026 Ваше Имя <you@example.com>
// SPDX-License-Identifier: GPL-3.0-or-later
```

Существующие копирайты не удаляйте и не переписывайте. Если правка в чужом файле существенная, допустимо добавить свою строку рядом.

Для файлов с build-тегами заголовок идёт **выше** `//go:build`, через пустую строку:

```go
// Copyright (C) 2026 Ваше Имя <you@example.com>
// SPDX-License-Identifier: GPL-3.0-or-later

//go:build android

package httpx
```

## Перед отправкой PR

```bash
gofmt -l .        # должно быть пусто
go vet ./...
go test ./...
```

Кросс-компиляция под все целевые платформы (ломается чаще всего из-за build-тегов):

```bash
for p in android/arm64 windows/amd64 darwin/arm64 linux/amd64; do
  CGO_ENABLED=0 GOOS="${p%%/*}" GOARCH="${p##*/}" go build ./... || echo "FAILED: $p"
done
```

## Архитектура

Проект следует гексагональной архитектуре — зависимости направлены внутрь:

- `internal/domain` — типы и порты (интерфейсы). Не зависит ни от чего, кроме стандартной библиотеки.
- `internal/services` — адаптеры: HTTP, ffmpeg, парсинг HLS, файловая система.
- `internal/app/kinopub` — сборка зависимостей и оркестрация прогона.
- `internal/lib` — самостоятельные утилиты (`webvtt`, `fsutil`, `httpx`, `logx` и др.).
- `cmd/kinopub` — разбор флагов и точка входа.

Новую логику отбора и разбора старайтесь размещать в `domain` или `lib` — она получается чистой и легко тестируемой без сети и без ffmpeg.

## Стиль

- Комментарии объясняют **почему**, а не **что**. Особенно ценны те, что фиксируют неочевидное решение или обойдённые грабли.
- Новое поведение сопровождается тестом. Тесты не должны требовать сети, ffmpeg или реального TTY.
- Ошибки оборачивайте через `%w`, чтобы работал `errors.Is`.
- Пользовательские сообщения — на английском (как и весь вывод утилиты), документация — на русском.

## Сообщения о багах

Полезно приложить:

- версию (`kinopub --version`) и платформу;
- полную команду (замаскировав куки);
- вывод с флагом `-v`;
- что ожидали и что произошло.
